# HAE-VAD Core

**Hearizon Audiology Engine — Voice Activity Detection**

### 面向实时字幕的流式语音活动检测与切句引擎

> 作者 **何瑞程**（He Ruicheng）· 北京语言大学 海南国际学院
> 独立实现 · 不基于 webrtcvad / Silero / pyannote 任何现有工程 · MIT 许可

---

实时字幕有一个和会议转录、离线识别都不同的约束：**切句的正确性直接决定字幕的可读性**。
等两秒才出字，字幕就没意义；切掉一个词首的 `/s/`，"Spanish" 就变成 "fan"；门限写死，
换个房间就失效。这三件事必须在同一个判决里同时满足，而现成的 VAD 都是为「有没有人说话」
设计的，不是为「切出来的片段能不能被正确识别」设计的。

HAE-VAD 按后者设计。判据是因果的、门限是自适应的、边界是回补的。

32 KB Python 包，或一个 17 KB 的 C++ 单头文件。Python 侧只依赖 numpy，C++ 侧零依赖。

```python
import hae_vad

seg = hae_vad.Segmenter(rate=16000, config=hae_vad.FAR)
for block in stream():                 # 每块 30 ms
    for sentence in seg.push(block):   # 切出来就交出去
        asr(sentence)
```

## 为什么另写一个

实时字幕对切句的要求可归纳为四条硬约束，每条都对应一个具体失败模式：

| 约束 | 违反后的现象 | 常见实现的做法 | 这里为什么不行 |
|---|---|---|---|
| 尾部延迟不能长 | 出字慢，字幕追不上语速 | 固定 1–2 秒静音才断句 | 延迟必须压在 700 ms 级 |
| 不能切在词中间 | Spanish → fan | 按固定静音时长切 | 词首擦音能量低，会被当静音 |
| 门限不能写死 | 换房间就失效 | 提供「灵敏度」滑块 | 用户不该为环境负责 |
| 不能只看能量 | 风扇被当人声，一直不收句 | 单阈值 RMS | 键盘、空调能量和轻声说话一样高 |

四条约束彼此冲突：延迟要短就得早断句，早断句就容易切在词中间，切在词中间就得回补，
回补又要求一直缓存历史音频。这里给出的是一组同时满足四条的参数化方案，而不是针对
某一个场景的特调。

## 判决模型

设第 t 个分析块（默认 30 ms）的能量为 e[t]（RMS），过零率为 z[t]。判决分三层。

### 第一层：自适应门限

维护一个长度 180 的滑窗 E[t]，里面是最近 180 个分析块的能量 e[t]，取其中第 20 百分位：

$$
T_t = \max\left(\tau_{\min},\; \kappa \cdot Q_{20}(\mathcal{E}_t)\right)
$$

用低分位而不是均值，是因为底噪的定义就是「持续存在的最低电平」。一声关门声会把均值抬高
零点几秒，但不该把门限抬高五秒钟。分位数天然对孤立脉冲免疫。

W = 180 块约 5.4 秒：短于一次正常的说话间隙，长于一次关门或咳嗽的影响窗口。

**因果顺序是硬约束。** 必须先算 T[t]、再判断 e[t]，最后才把 e[t] 并入窗口。顺序反了
会出现一个致命的自指：一块响亮的语音先被并进窗口，门限瞬间抬到它自己之上，然后它自己
就被判成静音。这个顺序在代码里有注释，改动前请想清楚。

### 第二层：过零率互证

$$
v_t = \left[\, e_t > T_t \,\right] \;\wedge\; \left[\, z_t < \zeta \,\right]
$$

白噪声、风噪、嘶声的过零率集中在 0.45 以上——这是白噪声的一阶统计性质决定的，不是调出来
的经验值。人声（含元音共振峰）在 0.02–0.25。

ζ 默认取 0.45 而非 0.55。取 0.55 时白噪声会漏过去，因为它的理论期望恰好是 0.5；
取 0.45 的代价是孤立的 `/s/` `/sh/` 可能被判成非人声——但它们几乎不单独成句，相邻元音会把
整块的过零率拉下来。

### 第三层：状态机与边界修饰

判决 v[t] 送入状态机，处理挂起、最短语音、最长语音、预录回补与尾部裁切：

```
静音 → 语音：接上预录缓冲（preroll_ms）
语音 → 静音：累计挂起时长，超过 hang_ms 触发切句
切句：尾音按能量谷底裁切，留 pad_ms 余量
```

只有第三层是「工程」——前两层是判决，第三层是把判决变成可用的片段。

## 四条与常见实现不同的设计

### 一、门限从环境里估，不写死

见上一节的 T[t]。这条消掉了「灵敏度」这个参数：用户不需要知道自己在什么声学环境里，
系统自己会测。

实测：安静办公室底噪约 0.003，开着空调的教室约 0.012，门限自动跟着从 0.008 走到 0.03。
固定门限在其中任一环境里都会有一半时间失效。

### 二、过零率做第二道闸

见上一节的 v[t]。这条是能量判据无法替代的：风扇的能量可以高过轻声说话，但过零率不会。

### 三、起句回补 300 ms

静音期间持续缓存最近 `preroll_ms` 的音频，判决转为语音的那一刻，把缓存接到句子前面。

这条**不是**可选优化，是修 bug 的必需品。`/s/` `/f/` `/θ/` 的词首是擦音，能量比元音低
15–25 dB，会被门限切掉。**这就是 "Spanish" 被识别成 "fan" 的根因**——不是模型不认识这个词，
是音频里根本没有那个 `/s/`。

300 ms 是权衡值：太短救不回词首，太长会把上一句的尾巴带进来。

### 四、尾音按能量谷底裁

切下来的片段尾部必然带一段静音（挂起时长 `hang_ms`）。对识别不是坏事——模型需要一点
上下文才确认「说完了」——但太长会拖慢，也可能让模型开始编内容。

做法是在尾部 320 ms 内逐窗搜索，找第一个能量低于峰值 2% 的位置，从那里切开，再留 40 ms
余量防止切在字中间。

流式临时结果用另一套更轻的算法（`trim_to_valley`）：只按平均能量从尾部剥掉明显安静的部分，
不做逐窗搜索。理由是临时结果只影响「边说边出字」的显示，不需要精确。

## 设计原则

**一、判决与修饰分离。** 判决层只回答「是不是语音」，返回布尔；修饰层决定边界怎么裁。
两层不共享状态，所以任何一层的改动都不会悄悄影响另一层。

**二、对脏输入安全降级。** 空块、超短块、全零、NaN——原样返回或安全跳过，不抛异常。
实时链路上一帧坏数据不该把整条流打断。

**三、两套实现必须逐位一致。** 中间运算全部走 float64，分位数用固定插值公式、稳定排序，
不依赖任何「版本间可能有差异」的库函数。Python 与 C++ 在同一输入上给出同一串数字，
`tests/run_parity.py` 逐行验证 21 行输出。

**四、只依赖标准库。** C++ 侧是 17 KB 单头文件，无动态分配热点、无全局状态，
可以直接放进实时线程或嵌入式。

## 五个预设与实测

参数以 `hae_vad/config.py` 的 `_PRESETS` 为准，下表由代码直接导出，不是手抄：

| 预设 | 场景 | `far_field_scale` | `floor_factor` | `min_rms` | `zcr_max` | `hang_ms` | `max_speech_ms` |
|---|---|---:|---:|---:|---:|---:|---:|
| `default` | 笔记本内置麦克风、安静房间 | 1.00 | 2.40 | 0.008 | 0.45 | 700 | 12000 |
| `near` | 贴着电脑说话（与 `default` 参数相同，语义别名） | 1.00 | 2.40 | 0.008 | 0.45 | 700 | 12000 |
| `far` | 四五米以上 | 0.65 | 2.40 | 0.008 | 0.45 | 900 | 15000 |
| `noisy` | 空调、风扇、多人 | 1.00 | 3.20 | 0.012 | 0.50 | 700 | 12000 |
| `aggressive` | 极小声也要收 | 0.45 | 2.40 | 0.005 | 0.45 | 900 | 15000 |

三个关键参数的作用：`far_field_scale` 把门限再乘一个系数（1.0 表示不降门限，只有远场类预设才小于 1）；`floor_factor` 决定动态门限 = max(`min_rms`, 底噪 × 这个倍数)；`zcr_max` 是过零率上限，白噪声的理论过零率就是 0.5，设到 0.5 等于不拦。

60 秒音频（20 个「说 2 秒、停 1 秒」周期），16 kHz，30 ms 一块：

| 预设 | 切句数 | 用时 | 实时倍数 |
|---|---:|---:|---:|
| `aggressive` | 20 | 202.2 ms | **297×** |
| `default` | 20 | 192.9 ms | **311×** |
| `far` | 20 | 194.8 ms | **308×** |
| `near` | 20 | 178.6 ms | **336×** |
| `noisy` | 20 | 179.2 ms | **335×** |

> 测试环境：AMD Ryzen 9 9955HX，32 GB，Windows 11 专业工作站版，CPython 3.12.14，numpy 2.3.5。
> 实时倍数对 CPU 型号与 numpy 版本很敏感，换一台机器差两三倍是正常的，看数量级即可。

切句延迟（= 凑满 `hang_ms` 所需的整块数 × 块长）：`default` / `near` / `noisy` 720 ms，`far` / `aggressive` 900 ms。
单实例内存约 20 KB（底噪窗口 1.4 KB + 预录缓冲 18.8 KB）。

> 以上是合成与受控录音上的数字，反映算法取舍，不等于任意场景下的识别率。真实效果请用
> 自己的录音跑一遍，对比切出来的片段与实际句子边界。

```bash
pip install numpy
git clone https://github.com/eyru/HAE-VAD-Core.git
cd HAE-VAD-Core
pip install -e .
```

### 作为库

```python
import hae_vad

seg = hae_vad.Segmenter(rate=16000, config=hae_vad.NEAR)

for block in blocks:                    # 每块 30 ms 的 float32 数组
    for sentence in seg.push(block):   # 切出来的完整句子
        asr(sentence)

    partial = seg.partial()             # 临时结果；未到刷新间隔时是 None
    if partial is not None and partial.size:
        asr_preview(partial)

tail = seg.flush()                      # 流结束时把最后一句吐出来
```

### 命令行

```bash
hae-vad in.wav                       # 用 near 预设切句，打印边界
hae-vad in.wav -p far -o out/        # 指定预设，把每句写成独立 wav
hae-vad --print-configs              # 列出所有预设
```

## 在 C++ 里使用

`include/hae_vad.h` 是同一套算法的单头文件实现（C++17，只依赖标准库）。

```cpp
#include "hae_vad.h"

hae::vad::Segmenter seg(16000, hae::vad::presetFar());

for (/* 每块 30 ms */) {
    auto sentences = seg.push(block.data(), block.size());
    for (auto& s : sentences) feedToAsr(s);
}

auto tail = seg.flush();
```

零依赖、无全局状态，可放实时线程。

## 参数参考

| 参数 | 作用 | 调大会怎样 |
|---|---|---|
| `min_rms` | 门限绝对下限 | 太小会把数字静音也当语音 |
| `floor_factor` | 门限相对底噪的倍数 | 越大越保守，容易漏掉轻声 |
| `floor_size` | 底噪窗口长度（块数） | 越长越稳，但适应环境变化变慢 |
| `zcr_max` | 过零率上限 | 越小白噪声挡得越干净，但擦音也更容易被挡 |
| `hang_ms` | 说停多久算说完了 | 越大越不容易切碎，但延迟变长 |
| `min_speech_ms` | 最短句子长度 | 太小会产出碎片，太大首句会被吞 |
| `max_speech_ms` | 最长句子长度 | 到点强制切断，防止一句话拖太久 |
| `preroll_ms` | 预录回补长度 | 救词首，太长会带进上一句尾巴 |
| `valley_ms` | 尾音搜索范围 | 越大越能找到真正的谷底，但耗时增加 |

## 与现有方案的定位差异

| 方案 | 定位 | 与本库的差异 |
|---|---|---|
| **HAE-VAD** | 为实时字幕的「可识别片段」设计 | 门限自适应 + 过零率互证 + 边界回补 |
| `webrtcvad` | 通话场景的语音检测 | 门限固定三档，无回补，切点不可控 |
| Silero VAD | 通用神经网络 VAD | 需要 onnx 模型，CPU 开销高一个量级，切点仍要自己修饰 |
| pyannote | 说话人分离与 VAD | 面向离线批处理，延迟不可接受 |
| 能量阈值 + 固定静音 | 最朴素的实现 | 换房间失效，切点在词中间 |

选择逻辑：需要「极低延迟 + 片段可识别」，这个库合适；需要「谁在说话」，用说话人分离；
需要「背景是持续稳态噪声」，先过 [HAE-NSG-Core](https://github.com/eyru/HAE-NSG-Core) 再切句。

## 已知局限

- **单声道、16 位 PCM wav**。其他格式需要自行解码成 float32 数组。
- **不检测音乐**。持续的音乐会被判成语音并切成句。
- **不处理双讲**。两人同时说话会被当成一个长句。
- **过零率对气声、嘶哑的声音偏保守**。这类声音的过零率天然偏高，可能被判成非人声，
  可以把 `zcr_max` 调到 0.55 或 0.6。
- **不含降噪**。切句前是否需要增强，交给上游决定。

## 验证方式

```bash
python -m unittest discover -s tests      # 37 项单元测试
python tests/run_parity.py                # Python 与 C++ 逐行对拍
python bench/bench.py                     # 速度与切句统计
```

对拍输出：

```
$ python tests/run_parity.py
对拍通过：21 行逐行一致
```

比对内容是完整切句结果（每句样本数逐个相同）、`rms` / `zero_crossing_rate` / `percentile`、
`partial` 调用序列、底噪估值、两种裁切函数。逐位一致意味着两套实现不是「结果接近」，
而是同一个输入产生同一串数字。这是双实现能被信任的前提。

对拍需要 MSVC（`cl.exe`）。没装的话脚本会跳过并说明原因。

## 相关项目

Hearizon Audiology Engine 拆成两个独立模块，加一个把它们装进实际产品的应用：

| 项目 | 作用 |
|---|---|
| **HAE-VAD Core**（本项目） | 语音活动检测与切句：让句子切得准 |
| [HAE-NSG Core](https://github.com/eyru/HAE-NSG-Core) | 噪声抑制与增益：让声音听得清 |
| [Hearizon Sync](https://github.com/eyru/HearizonSync) | 实时字幕翻译软件，Python 实现 |
| [HearizonSync C.R.V.](https://github.com/eyru/HearizonSync-CRV) | 同一产品的 C++ 重写版 |

推荐链路：

```
麦克风 → HAE-NSG → HAE-VAD（本库）→ ASR → 翻译
```

先增益再切句，是因为小声音被抬起来之后，切句的能量门限才有意义。反过来先切句再增益，
远场说话会被直接判成静音丢掉。
